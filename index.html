Bounded software builds with exact handoffs

This repository is the continuity layer between GPT/browser planning, GitHub revision identity, local OpenCode execution, committed evidence, and GPT/browser audit. The human-readable page and the agent-readable contract describe the same workflow.

Non-circular rule

A commit cannot contain its own final SHA and a hash manifest cannot recursively hash itself. Therefore the expected hub commit is supplied in the external execution handoff, while the prompt-pack digest is:

sha256(phase_N/manifests/pack.files.sha256)

The manifest covers immutable inputs but excludes itself, its digest file, the mutable ledger, reports, and runtime evidence.

OpenCode execution contract

Freshness gate

The installed binary is the execution syntax authority. The runner captures:

opencode --version
opencode run --help

It verifies required flags before execution and hashes the exact help snapshot for audit.

Approval boundary

--auto is deliberately not silent. The wrapper only adds it when the human explicitly invokes the wrapper with --auto.

./phase_0/commands/run-builder.sh \
  "$EXPECTED_HUB_COMMIT" \
  "$EXPECTED_PROMPT_PACK_SHA256" \
  --auto

Completion contract

OpenCode exiting successfully is not sufficient. A completed build needs committed evidence for:

result commit SHA
clean / dirty working tree
files changed
build + verification commands
verification results
known failures
unresolved issues
scope deviations
generated artifacts
OpenCode version
exact run-help hash
OpenCode transcript
mechanical Git evidence

Intentional repository changes must be committed. Unexplained residue is audit evidence, not something to hide.

GPT/browser audit loop

inspect exact result commit
↓
re-open exact sealed builder prompt
↓
compare required work with repository evidence
↓
inspect tests + runtime/mechanical evidence
↓
check scope + dirty residue + unresolved failures
↓
PASS / REPAIR / BLOCK
↓
write audit into build_ledger.yaml

PASS means required work is supported by committed evidence. REPAIR means a bounded repair phase can address defects. BLOCK means provenance/evidence is broken or continuing would require guessing.

Trust / security boundary

SHA-256 proves

Byte identity relative to a digest, corruption detection, and reproducibility.

SHA-256 does not prove

Who authored the digest, that GitHub was never modified, or that a repository is trustworthy.

Hard stop: credentials, API keys, private keys, tokens, sensitive .env contents, or other secrets must not enter prompt packs, commit-bound transcripts, or reports. If found, stop before commit.

Future hardening may add signed commits/tags, branch protection, release manifests, or CI attestations. Phase 0 does not require them.

Golden path

# 1. edit the phase
$EDITOR phase_0/manifests/build-inputs.yaml
$EDITOR phase_0/prompts/builder.md

# 2. seal immutable inputs
./phase_0/commands/seal-pack.sh

# 3. commit + push hub phase
git add index.html README.md WORKFLOW.md VERIFICATION.md phase_0
git commit -m "phase0: seal bounded builder pack"
git push

# 4. external execution handoff
EXPECTED_HUB_COMMIT="$(git rev-parse HEAD)"
EXPECTED_PROMPT_PACK_SHA256="$(cut -d' ' -f1 phase_0/manifests/PROMPT_PACK_SHA256.txt)"

# 5. prepare exact source
./phase_0/commands/prepare-workspace.sh

# 6. verify identity
./phase_0/commands/verify-inputs.sh \
  "$EXPECTED_HUB_COMMIT" \
  "$EXPECTED_PROMPT_PACK_SHA256"

# 7. execute
./phase_0/commands/run-builder.sh \
  "$EXPECTED_HUB_COMMIT" \
  "$EXPECTED_PROMPT_PACK_SHA256" \
  --auto

# 8. audit exact result commit
# 9. update build_ledger.yaml with PASS / REPAIR / BLOCK
# 10. commit + push hub evidence
